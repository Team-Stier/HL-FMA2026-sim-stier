# North recovery control diagnosis and brake-release correction

The shorter lateral convergence improved road tracking early in the north curve but did not complete the route. At matched positions, signed road-centerline error changed from -0.280m to -0.085m near x=820, and -0.396m to -0.210m near x=825. It grew again to -0.377m near x=830 (original -0.385m). Thus an earlier final stop does not mean the whole recovery geometry was worse.

Before the final stop, all 169 replayed controller frames had a valid reference and successful MPC solution. Current-path lateral error maximum was 0.00815m, heading error maximum 0.302 degrees; those small errors coexist with growing road error because each new path starts from the evolving Ego pose. Path age median/max was 0.120/0.372s; Ego age 0.0194/0.0726s. Replayed steering matched actual output within 0.00110rad (p95 0.0000304rad). No sign inversion, projection failure, solver failure, steering saturation, or new timing-grid defect was established before the planner rejection.

The first final braking command was at 1789080713.350984 with STOP_STALE_SPEED_LIMIT, followed by the first empty Path at 1789080713.374068 and STOP_NO_LOCAL_PATH at 1789080713.401386. Correlation uses the nearest same-tick status, not the previous status. Neutral steering requests were rate-limited while -3m/s² braking remained immediate. The path's failing captured state predates these braking commands. Independent planner replay at Ego stamp1789080713289339454 found all15 candidates rejected at roadSample index0: the current whole footprint was already outside the allowed corridor. Curvature0.01050/m was valid. The preceding path also initially bent outward (d=-0.34984m at start, -0.40195m at2m, -0.43459m at5m), so geometry convergence remains a separate planner issue.

The reported maximum 9.068m/s is a source timestamp speed-estimation spike: a 0.298613m displacement divided by 32.929ms is 9.068m/s; the next 0.299230m divided by 47.382ms is 6.315m/s. The centered 200ms XY speed is 7.482m/s. It does not demonstrate a physical acceleration to 9.068m/s. It does trigger the current overspeed override.

A separate, concrete controller defect was exposed by that spike: command acceleration went from -3.0 at 1789080710.700963 to +0.207793 at 1789080710.751529. The override replaced the PI result after its previous_acceleration state had been recorded, so release used the old PI output instead of actual braking. This is not claimed to explain the entire corner failure.

Authorized minimal correction in src/control only: setAppliedAcceleration records the finite/clamped actual float acceleration in the common publication path. Longitudinal reset now clears integral and measured-speed history while retaining the previous acceleration; otherwise a reset would recreate the same release discontinuity. Immediate fault/overspeed braking remains unchanged. No model gain, wheelbase, configuration tuning, new messages or package coupling was added.

The real-node regression reproduces the pre-fix failure with source speeds 9.068 then 6.315m/s: after immediate -3m/s² braking the old binary released to +1.1714m/s² in the test fixture. The new test requires continued negative acceleration immediately after release and checks that every subsequent upward command change stays within 3m/s³ times the control interval, including faults and reset recovery. Core tests also check the exact -3 to -2.85 first recovery step and eventual positive acceleration.

Observed physical yaw response remains speed dependent: latest run's best delay fit was 100ms (previous runs about70ms), 7–8m/s effective yaw gain 0.835 relative to v*tan(delta)/2.944, versus0.971 at2–4m/s. These are observational response fits, not validated calibration constants. No arbitrary gain or MPC replacement is warranted within this bounded fix; persistent curve tracking needs a separate controlled actuator/model validation and planner geometry follow-up.

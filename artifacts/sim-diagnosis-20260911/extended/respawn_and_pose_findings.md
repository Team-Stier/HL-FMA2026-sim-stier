# 확장 주행의 시작 위치와 자연 리스폰 분리

저장소·원본 checkpoint·설정 수정 없음. 아래 시간은 observer의 wall clock epoch이며 `actions.jsonl`과 대조했다. 이 문서는 최초 sweep의 계측 영향을 분리하기 위한 기록이다. 부모가 동일 원본 controller/planner를 매 case 새 프로세스로 띄우는 clean sweep을 따로 진행했다.

## 북쪽 오르막 최초 배치는 정상

`north_uphill_road2819` 요청은 t1789073914.848549의 `(1435.540361846,1097.397598207,z47.782799491,h-1.529395636)`였다. 첫 새 ego t3914.860998은 `(1435.540405273,1097.397583008,z47.782798767,h-1.529395580)`로 요청과 일치한다. 이후 약3.5초 정지한 채 위치와 높이가 유지됐고 footprint cell들은 예정 lane445027에 속했다. 원본 IntersectionMonitor도445027을 선택한다. 시작하자마자 높이가 달라져 리스폰된 사례가 아니다.

SIGCONT 기록 t3918.354355 뒤에는 `FORWARD_STALE_EGO`와 조향0/가속+2.0m/s² 명령이 지속됐다. 다른 subscriber인 observer는 fresh ego를 받았고, 새 planner는 `[445027,445452,446279,500918,448217]` route와 로컬 패스를 발행했다.

1097→648m 이동은 연속 가속이며 거대한 최초 리스폰 한 번으로 설명되지 않는다. 이 두 case(북쪽 오르막, 다음 서쪽 동향)의 장시간 폭주를 정상 경로 추종 실패 통계에 포함하면 안 된다. SIGSTOP으로 controller 프로세스를 멈추는 초기 시험 방식과 연관된 입력 수신 단절이 확인됐다.

control agent의 직접 증거: PID142382의 FastDDS SHM port7415 mapping이 `(deleted)` inode770047이었고 다음 SIGCONT t4228.420에 새 inode805936으로 controller/tracker 모두 다시 연결되며 ACTIVE가 복구됐다. 자세한 구분은 [input_freeze_evidence.md](/tmp/control_roadscan/input_freeze_evidence.md). DDS 내부의 정확한 삭제 호출 경로까지 입증한 것은 아니다. 입력 단절을 일으킨 계측과, 입력이 없어도 계속 가속하는 fallback 정책은 별개 문제다.

## 후속 재배치 자체는 확인되지만 모든 트리거를 판정할 로그는 없음

Traffic 로그에는 시험 `actions.jsonl`에 없는 다음 SCP Set/Speed0가 있다.

- `(1475.3541,222.8426,z60.3798,h-81.1956deg)`
- `(1464.6717,186.2215,z59.1378,h9.1042deg)`
- `(1509.5447,171.7386,z59.1378,h99.0829deg)`
- `(1480.5551,368.7148,z61.3427,h92.3137deg)`

t3955.980747에서 위치5.8565m/방향2.1254rad가78.7ms 사이 바뀌고, t3963.462300에서는 위치6.4420m/방향2.1348rad가41.2ms 사이 바뀐다. 원격 명령 로그와 일치하므로 자연 복구 과정의 재배치 증거다. 반면 단순 `distance>4m` 표시는50m/s×80ms의 정상 이동도 잡으므로 자동으로 respawn이라 부르면 안 된다.

`/tmp/taskRec_ModuleManager.txt`는50,741,679byte로 파일 크기 제한 근처에 도달해 **05:16 이후 갱신되지 않았다**. `/tmp/taskRec_Traffic.txt`는 계속 갱신된다. ModuleManager의 오래된 `[RESPAWN] reason=rdb_offroad` 문구를 현재 sweep 재배치의 원인 증거로 사용하지 않았다. 현재 발생 각각이 offroad 판정인지 다른 복구 조건인지 확정할 수 없는 범위가 남는다. 시작 높이 오류는 위의 정지/주행 초기 증거와 맞지 않는다.

- `actions.jsonl`: 사용자가 허용한 부모의 실제 재시작/이동 및 controller 재시작 기록.
- `events.jsonl`: ego, status, command, cap, route, path, cell 요약.
- `north_uphill_initial_run.json`: 최초 북쪽 case 초 단위 상태와 위치/방향 불연속 후보. 후보 목록에는 빠른 정상 이동도 포함되므로 시간/명령 로그와 함께 해석.
- [topology_findings.md](/tmp/sim_diagnosis_extended/topology_findings.md): 시작점/방향/지도 topology 원본 검증.
- [respawn_findings.md](/tmp/sim_diagnosis_20260911/respawn_findings.md): 이전 정상 재시작에서 확인한 새 ego+옛 route 혼합580.7m 경로, 교차로 respawn 뒤6.426초 global freeze. 최초 sweep의 DDS 장애와 별개로 확인된 현상.

## 마지막 북쪽 clean run: 상부 도로에서 하부 평행 도로로 이동

최종 정지 ego `(1454.143554688,852.031982422,z49.418167114,h-0.997943699)`는 lane471691(road3018)의 centerline `(1454.104059137,852.030165807,z49.418168261)`에서0.03954m 떨어져 있다. 목표448217(road2820)의 가장 가까운 centerline은 `(1445.946169216,851.692397189,z52.923731967)`로8.20442m 떨어져 있고3.50556m 높다. 목표 xy까지는32.45758m가 남았다. 471691→448217의 원본 routing graph shortestPath는36lane이며 실제 새 global route 앞부분 `[471691,479093,404656,404247,403838]`과 일치한다. 여기서 긴 돌아가는 경로는 새 위치에 근거한 정상 재탐색이다.

상부→하부 이동 직전의 연속성은 다음과 같다.

- t1789074631.620: `(1447.322876,865.043884,z52.936314,h-0.921600,v9.398)`.
- t4631.660: `(1447.083496,865.331848,z52.923733,h-1.529468)`. 40ms 사이0.374m 되돌림과 방향-0.608rad 변화. 이후 이 위치에서 약0.44초 정지.
- t4632.100까지 위 위치, speed0.
- t4632.179741: `(1448.383057,861.187134,z48.970463,h-1.131964,v54.413)`. **79.4ms 사이 XY4.34368m, Z-3.95327m 점프**.
- 이후 낮은 road3018에서 연속 이동 후 위 최종점에 정지.

따라서 자연스러운 연속 주행만으로 상부→하부 전이를 설명할 수 없다. 이 구간의 native Traffic 로그에는 마지막 시작 pose Set 이후 추가 Set 로그가 없다. ModuleManager는 이미 capped 상태여서 구체적인 simulator 접촉/복구/도로 표면 스냅 트리거는 **확인되지 않았다**. 바로 앞의 heading 변화와 제어/로컬 패스는 별도 원인 분석 대상이다. 자료: `north_upper_to_lower.json`. 이 사건을 앞서 증명한 교차로 global freeze와 합쳐 설명하지 않는다.
